# watchdog

A scheduled script (GitHub Actions, every 5 minutes, no AI) that finds late work in the Alphatoris Library records and wakes whoever owns it. This repository holds only the script, its workflow, tests, and a `status` branch. It holds no project data: the public status feed has, per opaque project id, only the stage number, a fixed state word and counts of open and late items (owner decision of 28 October 2026 16:05 UTC: counts only, no names, times or free text), and the state file keys are hashes.

Secrets (repository secrets, never in files): `READ_KEY` (read-only Library key), `WAKE_URL`, `WAKE_KEY` (wake runner).

Run the tests: `python3 -m unittest -v tests/test_watchdog.py`
Dry run on fixtures: `python3 watchdog.py --out /tmp/out --fixtures <dir> --dry-run`

Unverified until live: the exact request format of the wake runner's fire endpoint (`fire_wake` in `watchdog.py`).

## PR-comment wake (fast route)
Per project, a long-lived draft "wake page" pull request in this repository (never merged; not locked, because a locked page refuses the Actions bot; the relay acts only on comments by github-actions[bot]). At ladder step 1 the script comments `Watchdog wake: <label> step 1` there with the workflow token (`pull-requests: write`). A standing thread of the project is subscribed to that PR; it wakes in seconds, replies with the single word `ack` (never project detail; the script counts only non-bot comments created after the wake by an OWNER, a MEMBER, or the configured agent account `alphatoris-agent`, matched by id and login together, which GitHub reports as COLLABORATOR), and messages its coordinator. The registry entry holds `wake_pr` (`owner/repo#n`, validated), and `wake_subscriber` (`session_id`, `subscribed_at`, not in the future; there is no age limit, a dead or replaced relay is caught by the acknowledgement check). After a lost wake the project keeps `wake_route` `pr_unacked` on the feed, even when nothing is late, until a non-bot owner, member or agent-account comment appears on the wake page after the lost wake (a relay that re-subscribes can post `ack` to clear it). No ack within 2 ticks, a refused comment, a malformed `wake_pr` or a shared one: the item falls back to the wake runner and the hourly guard, and the feed shows `wake_route` `pr_unacked`, `pr_failed` or `hourly_guard_only`; while the fast route is healthy it shows `pr_comment`. At most one step-1 comment is posted per project per tick, however many items went late together; each item keeps its own ladder state and is acknowledged against that one comment. The comment text is only the label and the step, never item ids. Step 2 is also a bot comment, but on the Delivery Lead's wake page (the registry project `delivery-lead`), not the wake runner: the registry's session id can go stale after a rotation, the page does not. The text is `Watchdog wake: <Delivery Lead label> step 2 (for <late project's label>)`, opaque labels only, no item ids. At most one such comment per late project per tick, and each item is acknowledged on its own. The runner is used instead when the Delivery Lead has no usable page (no subscriber, paused, shared page, route mark or daily probe down), when the late project is the Delivery Lead itself, when the comment is refused (same tick), and when it is not acknowledged within 2 ticks (sent again once by the runner). Step 3 never uses the PR.

Owner alerts (ladder step 3) go by severity, not by time (playbooks rev-055, cycle rules section 21 item 3): the old step 3 after 4 ticks is removed. Only an open item marked `"severity": "critical"` (security, data or major failure) goes to the owner, at once and once, ahead of steps 1 and 2. Time alone never reaches the owner; items for the Delivery Lead only and reserved items never go to the owner by the watchdog. The owner send is separate from steps 1 and 2: if it fails it is retried on later ticks and never holds back the coordinator or the Delivery Lead. An item that is re-dated, or goes late again, gets a new key and alerts the owner again. Whether a blocker is material enough to need Aamer is the Delivery Lead's judgment, not a watchdog step.

Delivery Lead requests to a project (playbooks rev-058 section 17 items 3 and 6): a relay is not woken by comments from its own account, and the Delivery Lead and the relays all post as `alphatoris-agent`, so the bot comment stays the only wake (Q12). The Delivery Lead files the request in its own list (`projects/delivery-lead/stages/OPEN-ITEMS.json`, the registry project `delivery-lead`) with `"project"` set to the target's registry id and `due` equal to `given`. Such an entry counts as a late item of THAT project under the usual late rules: step 1 is the target's wake PR comment (same ack, `pr_unacked` fallback and one-comment-per-tick behaviour), step 2 the Delivery Lead, step 3 only if `severity` is `critical`. Its state key is prefixed `dl:`, so it cannot collide with a project item of the same id. A routed entry's step-1 comment names its request once, by id only: `Watchdog wake: <label> step 1 | Delivery Lead request <id>[,<id>]`. The request text stays in the Library list (the wake page is public); the relay passes the id to the coordinator, who reads that entry. Only move `due` forward: an earlier passed time starts a new ladder, and a changed `due` closes the old one. Reserved entries (owner contains "aamer") are not routed and never climb. An entry with no `project`, or one naming an unknown or paused project (stderr note only), is an ordinary Delivery Lead item, chased as before. Feed counts: a routed entry stays in the Delivery Lead project's `open` and `late` counts and is not counted under the target, so the public feed does not show which project was asked.

Daily probe: at 06:00 UTC, once a day, each project with a healthy wake subscriber gets a `Watchdog wake: <label> step probe` comment on its wake page. The relay acknowledges it like a wake. No ack within 2 ticks marks the relay down: the feed shows `pr_unacked` (or `pr_failed` if the comment was refused), and one late item, `relay-probe`, climbs the ladder (wake runner to the coordinator, then the Delivery Lead; it never reaches the owner by time). The mark clears on the next ack. A paused project or one without a subscriber is not probed.

Evidence gate word: each project's feed entry has `gate`, one word and never a milestone: `unknown` (no `ledger/status/<project>.json`, a paused project, or a failed read), `unreadable` (a status file without a readable milestone), `ahead` (the stage is shown more than one ahead of the computed milestone) or `ok`. A missing status file stays report-only (no late item), but it is now visible as `unknown` instead of silent.

A project whose `public_label` is missing, malformed or shared with another is still counted and woken; the feed shows it under a neutral index (`E0`, `E1`) with `error: bad_label`, and the hourly guard lists it for the coordinator. State keys are HMAC-SHA256 keyed with `READ_KEY` (or `STATE_SALT` if set), so they cannot be guessed from a project name.
