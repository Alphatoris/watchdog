# watchdog

A scheduled script (GitHub Actions, every 5 minutes, no AI) that finds late work in the Alphatoris Library records and wakes whoever owns it. This repository holds only the script, its workflow, tests, and a `status` branch. It holds no project data: the public status feed has, per opaque project id, only the stage number, a fixed state word and counts of open and late items (owner decision of 28 October 2026 16:05 UTC: counts only, no names, times or free text), and the state file keys are hashes.

Secrets (repository secrets, never in files): `READ_KEY` (read-only Library key), `WAKE_URL`, `WAKE_KEY` (wake runner).

Run the tests: `python3 -m unittest -v tests/test_watchdog.py`
Dry run on fixtures: `python3 watchdog.py --out /tmp/out --fixtures <dir> --dry-run`

Unverified until live: the exact request format of the wake runner's fire endpoint (`fire_wake` in `watchdog.py`).

## PR-comment wake (fast route)
Per project, a long-lived draft "wake page" pull request in this repository (never merged; not locked, because a locked page refuses the Actions bot; the relay acts only on comments by github-actions[bot]). At ladder step 1 the script comments `Watchdog wake: <label> step 1` there with the workflow token (`pull-requests: write`). A standing thread of the project is subscribed to that PR; it wakes in seconds, replies with the single word `ack` (never project detail; the script counts only non-bot comments created after the wake by an OWNER, a MEMBER, or the configured agent account `alphatoris-agent`, matched by id and login together, which GitHub reports as COLLABORATOR), and messages its coordinator. The registry entry holds `wake_pr` (`owner/repo#n`, validated), and `wake_subscriber` (`session_id`, `subscribed_at`, not in the future; there is no age limit, a dead or replaced relay is caught by the acknowledgement check). After a lost wake the project keeps `wake_route` `pr_unacked` on the feed, even when nothing is late, until a non-bot owner, member or agent-account comment appears on the wake page after the lost wake (a relay that re-subscribes can post `ack` to clear it). No ack within 2 ticks, a refused comment, a malformed `wake_pr` or a shared one: the item falls back to the wake runner and the hourly guard, and the feed shows `wake_route` `pr_unacked`, `pr_failed` or `hourly_guard_only`; while the fast route is healthy it shows `pr_comment`. At most one step-1 comment is posted per project per tick, however many items went late together; each item keeps its own ladder state and is acknowledged against that one comment. The comment text is only the label and the step, never item ids. Step 2 is also a bot comment, but on the Delivery Lead's wake page (the registry project `delivery-lead`), not the wake runner: the registry's session id can go stale after a rotation, the page does not. The text is `Watchdog wake: <Delivery Lead label> step 2 (for <late project's label>)`, opaque labels only, no item ids. At most one such comment per late project per tick, and each item is acknowledged on its own. The runner is used instead when the Delivery Lead has no usable page (no subscriber, paused, shared page, route mark or daily probe down), when the late project is the Delivery Lead itself, when the comment is refused (same tick), and when it is not acknowledged within 2 ticks (sent again once by the runner). Step 3 never uses the PR.

Owner alerts (ladder step 3) go by severity, not by time (playbooks rev-055, cycle rules section 21 item 3): the old step 3 after 4 ticks is removed. Only an open item marked `"severity": "critical"` (security, data or major failure) goes to the owner, at once and once, ahead of steps 1 and 2. Time alone never reaches the owner; items for the Delivery Lead only and reserved items never go to the owner by the watchdog. The owner send is separate from steps 1 and 2: if it fails it is retried on later ticks and never holds back the coordinator or the Delivery Lead. An item that is re-dated, or goes late again, gets a new key and alerts the owner again. Whether a blocker is material enough to need Aamer is the Delivery Lead's judgment, not a watchdog step.

Delivery Lead requests to a project (playbooks rev-058 section 17 items 3 and 6): a relay is not woken by comments from its own account, and the Delivery Lead and the relays all post as `alphatoris-agent`, so the bot comment stays the only wake (Q12). The Delivery Lead files the request in its own list (`projects/delivery-lead/stages/OPEN-ITEMS.json`, the registry project `delivery-lead`) with `"project"` set to the target's registry id and `due` equal to `given`. Such an entry counts as a late item of THAT project under the usual late rules: step 1 is the target's wake PR comment (same ack, `pr_unacked` fallback and one-comment-per-tick behaviour), step 2 the Delivery Lead, step 3 only if `severity` is `critical`. Its state key is prefixed `dl:`, so it cannot collide with a project item of the same id. A routed entry's step-1 comment names its request once, by neutral id only: `Watchdog wake: <label> step 1 | Delivery Lead request dl-<n>[,dl-<m>]`. The entry carries `"wake_id": "dl-<n>"`; an entry without one is woken without a request id. The descriptive id and the text stay in the Library list (the wake page is public, so a meaningful id would tie the label to a project); the relay passes the dl- id to the coordinator, who reads the entry with that wake_id. Because a relay acked and stopped (1 Nov, dl-58 to dl-64), the step-1 comment also carries a fixed instruction after the id: after ack, message your coordinator to act now on the request in the Delivery Lead list entry with that wake_id and report on the page with counts and labels only. The text names no project detail. Only move `due` forward: an earlier passed time starts a new ladder, and a changed `due` closes the old one. Reserved entries are not routed and never climb. An item is reserved when `reserved` is true or its owner contains "aamer" (fail closed), except an owner that starts with a project name that begins with the same word ("Aamer Wealth Intelligence ...", "Aamer OS ..."), unless `reserved` is true. An entry with no `project`, or one naming an unknown or paused project (stderr note only), is an ordinary Delivery Lead item, chased as before. Feed counts: a routed entry stays in the Delivery Lead project's `open` and `late` counts and is not counted under the target, so the public feed does not show which project was asked.

Checkpoints (Release 1.3 S2, audit 21d): an open item may carry an optional `checkpoint` time, and a registry entry already has `next_checkpoint`. The owner moves it forward at each check-in. Once it has passed, a late item reports the miss to the Delivery Lead only (step 2, never the coordinator, never the owner, even if critical): `checkpoint-missed:<item id>` for an item, `registry-checkpoint-missed` for an entry. The item's own list is read as before; a done, dropped or reserved item, a paused project, and a value that is not a time are ignored (the last with a stderr note). The checkpoint time is part of the state key, so moving it forward closes the report and a later miss starts a new one. A checkpoint on a Delivery Lead entry routed to a project is reported for the Delivery Lead's own list, not under the target. Feed counts: these count as late for their project.

One-minute wake for a new late item (Release 1.3 S2, audit 21a): the loop runs a pass every 60 s. Every fifth pass is the 5-minute tick (it counts, moves the ladder clock, and publishes the feed and tick log). The passes between are fast (`watchdog.py --fast`): they read the same records and send what is due, so a newly filed item whose `due` has passed wakes its owner at the next pass, within about a minute (plus the Library filing time and the read), but they do not increment the tick number, change `last_tick_at`, publish the feed, or write the tick log, and they save `state.json` only when something was sent or acknowledged. Every ladder timing (step 2 after 2 ticks, the 2-tick ack wait, the daily probe) still counts 5-minute ticks, so nothing else changes. Cost: about five times the Library reads (roughly 30 a minute, well inside the 5000 an hour limit of the read key). Not a guarantee: GitHub can delay the run's sleep, and the step-1 comment still depends on the relay.

Daily probe: at 06:00 UTC, once a day, each project with a healthy wake subscriber gets a `Watchdog wake: <label> step probe` comment on its wake page. The relay acknowledges it like a wake. No ack within 2 ticks marks the relay down: the feed shows `pr_unacked` (or `pr_failed` if the comment was refused), and one late item, `relay-probe`, climbs the ladder (wake runner to the coordinator, then the Delivery Lead; it never reaches the owner by time). The mark clears on the next ack. A paused project or one without a subscriber is not probed.

Evidence gate word: each project's feed entry has `gate`, one word and never a milestone: `unknown` (no `ledger/status/<project>.json`, a paused project, or a failed read), `unreadable` (a status file without a readable milestone), `ahead` (the stage is shown more than one ahead of the computed milestone) or `ok`. A missing status file stays report-only (no late item), but it is now visible as `unknown` instead of silent.

A project whose `public_label` is missing, malformed or shared with another is still counted and woken; the feed shows it under a neutral index (`E0`, `E1`) with `error: bad_label`, and the hourly guard lists it for the coordinator. State keys are HMAC-SHA256 keyed with `READ_KEY` (or `STATE_SALT` if set), so they cannot be guessed from a project name.

Send log: each line of `ticks.jsonl` now also carries `tick_no` and `sent`, a counts-only list with one entry per wake sent that tick: `label` (opaque), `step`, `route` (`pr_comment`, `dl_page` or `runner`), `runner_fired` and `ok`. No item ids, names or free text. A step-1 resend by the wake runner after an unacknowledged comment therefore shows in public data, and so does the one-step-per-tick order: the resend takes that tick, step 2 follows on the next.

Ack window in seconds: a wake comment (step 1 on a project page, step 2 on the Delivery Lead page) not acknowledged within 120 seconds is treated as lost, judged in every one-minute pass; ack reads happen only for a wake that is still waiting (a pending step 1 or step 2); the lost-wake route mark and the daily probe are judged on 5-minute ticks only, so a down relay costs no reads between ticks.
 Relays answered in 9 to 21 s on 31 Oct. When step 1 is lost the wake runner resends it at once, and step 2 goes to the Delivery Lead page on the next pass, so an unanswered step 1 reaches the Delivery Lead within about 3 to 4 minutes (audit item 20: 5 minutes). When step 1 was acknowledged, step 2 still waits its 2 ticks. This replaces the "2 ticks" ack window described above.

Read at a fixed commit: each pass first asks for main's commit sha (one extra call, `git/ref/heads/main`) and reads every Library file at that sha, because a read by branch name can be served from a cache for up to a minute and hid a new late item from one fast pass (live run 41224606606: admitted 17:28:56Z, woken 17:30:51Z). If the sha call fails the pass reads by branch name and says so on stderr.
